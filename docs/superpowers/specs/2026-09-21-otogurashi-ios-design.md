# オトグラシ iOS 製品・体験・技術設計

更新日: 2026-09-22（iOSのみ検証し、将来のAndroid転用に備える方針へ更新）
状態: 開発先OtoGrashiへ設計を移管。実装計画のレビュー段階。アプリ実装・実機検証は未着手。
対象: iPhone / iOS 18以降を提案。最低OSは製品上の選択であり、Appleの必須条件ではない。
開発: Windowsで編集、GitHub ActionsのmacOS環境でビルド、TestFlight経由でユーザーのiPhoneを使って検証する。
構成: Flutter/Dartで画面と主要ロジックを共通化できる形にし、録音・メディア処理等のiOS実装を分離する。Androidの実装・ビルド・動作検証・配布は初版の対象外。

## 1. 製品の約束

**いつもの物を3つ撮ると、その音でできた、自分の15秒が生まれる。**

ユーザーが欲しいのは、家具・家電・コップなど現実の物の音が音楽になる動画。
音楽経験のない人が「この音、私の家の音だ」と分かり、もう一つ撮りたくなることを目指す。
見た目はsetlogに通じる自然な日常動画の親しみやすさ。高級な作曲ソフトの雰囲気にはしない。

### ユーザーから確定していること

- iOS版として新規に作る。まず設計から詰め、完成版へつながる構成にする。
- 音を伴う短い生活動画を撮り、音楽動画にする基本コンセプトを維持する。
- UIのアートディレクションに実物の道具の形を使う。
- 撮影画面では上に開いた蓋、下にカップの飲み口と上部。左右にカップの枠は付けない。
- 長方形のスマホ画面内で成立させる。ほかの画面はタンブラーに統一しない。
- 「道具をタップして演奏する別のアプリ」は保留。今回の操作体系に入れない。
- 触って気持ちよく、人に共有したくなることを優先する。
- GitHub ActionsとTestFlightを普段使っている。実機のiPhoneがある。
- 当面のビルド・端末テスト・品質保証はiOSのみ。Androidは将来転用しやすい程度に備え、同時対応を進めない。

### 今回の設計で置く提案

- 3〜6クリップを使う。初回は3つに案内する。
- アカウント不要、基本処理は端末内。クラウド生成の待ち時間や通信を必須にしない。
- 15秒 / 縦9:16 / 1080p / 30fpsを初版の完成動画の基準とする。
- 初版は録った音をリズムに並べる決定的な音処理と、少量のオリジナル伴奏で曲を作る。
- 初版には公開フィードやコメント欄を作らず、iOS共有シートとリミックス用ファイルで人に渡す。
- ホームは「今日のクリップ」。初回のみ内蔵の短い体験作品から始められる。

## 2. 初版完成の定義

「撮影ができるデモ」で終わらず、次の一周が端末内で成立する製品を初版とする。

1. 説明を読む前に、内蔵サンプルで完成動画と元の音の違いを体験できる。
2. カメラ・マイクを許可して3つの音付き動画を撮る。または選択した動画を読み込む。
3. 自動で音を切り出し、3種類のアレンジを選んで聴ける。
4. 元の音との比較、素材の差し替え、音量・字幕・動画の見せ方の調整ができる。
5. 15秒の動画をプレビューして、写真アプリへ保存し、共有シートで渡せる。
6. 下書き・録った素材・完成作品が残り、再編集・再利用できる。
7. 相手に渡す素材を確認して、リミックス可能なプロジェクトファイルを共有できる。
8. 権限拒否・電話割り込み・容量不足・書き出し失敗から回復できる。

初版に含めないもの: 公開SNS、見知らぬ人とのマッチング、フォロワー数、連続ログイン罰則、物体検出による演奏UI、任意の楽曲の模倣生成。
これらは「共有したい」という目的に不可欠ではなく、元の体験を完成させる時間を優先する。

## 3. 主要な利用場面

### 初めての朝

コップを机に置く音、蛇口の水音、キーボードの音をそれぞれ3秒撮る。
「この音でつくる」を押すと、各音が少しずつ加わるプレビューが始まる。
気に入ったアレンジで「いつもの朝」という動画を保存する。

### もう一度作る夜

ライブラリから朝のコップを再利用し、電子レンジの終了音と椅子の音を加える。
自分の「音の引き出し」が増え、撮る負担が少なくなる。

### 友だちに渡す

動画はiOS共有シートから渡す。別途「この素材で遊んでもらう」から選んだ素材と編集情報をファイルで共有する。
相手はオトグラシへ読み込み、自分の音を一つ差し替えて別作品を作る。
相手にアプリがなくても、完成動画は通常の動画として見られる。

## 4. 画面と移動

基本タブは「つくる」「作品」「音の引き出し」の3つ。設定は各画面右上から開く。
撮影中はタブを隠し、キャンセル・録画・取り込みに集中する。存在しないSNSプロフィールは置かない。

| 画面 | 主な内容 | 主操作 | 戻ったとき |
| --- | --- | --- | --- |
| 初回体験 | 3つの生活音と完成15秒の内蔵サンプル | 聴いてみる / 自分の音でつくる | 次回から省略できる |
| つくる | 今日の素材3〜6枚、未完成作品の続き、撮影・取り込み | 音を撮る / この音でつくる | 下書きを保持 |
| 撮影 | ライブ映像、簡単な音量表示、3秒録画 | タップで開始、再タップで停止 | 保存済み素材を保持 |
| 撮影確認 | 1クリップのループ、名前、トリム | 使う / 撮り直す | 元の撮影画面 |
| 音づくり | 3アレンジ、選択中の音楽動画 | 聴き比べ / 調整 | 同じ時刻から戻れる |
| 調整シート | 素材の音量、使う音の位置、字幕、レイアウト | 完了 / 元に戻す | 適用済み変更を保持 |
| 完成 | 15秒プレビュー、タイトル、書き出し | 保存 / シェア | 作品に自動保存 |
| 作品 | 下書き・完成作品の一覧 | 再編集 / 複製 / 共有 | スクロール位置保持 |
| 音の引き出し | 元動画と音、名前、使用中の作品 | 再利用 / 整理 | 絞り込みを保持 |
| 共有ファイル確認 | 渡す動画・素材・作者名の一覧 | ファイルを作る | 選択状態を保持 |
| 設定 | 触覚、装飾量、容量、ヘルプ、購入復元 | 個別設定 | 遷移元へ戻る |

アプリ起動 → 初回体験またはつくる → 撮影/取り込み → 素材確認 → つくる
→ 音づくり → 必要なら調整 → 完成 → 保存/共有。

「作品」から再編集した場合は元の完成版を消さず、新しいリビジョンとして残す。

## 5. 機能仕様と価値

| 機能 | 振る舞い | うれしさ |
| --- | --- | --- |
| 3秒キャプチャ | 既定3秒、必要な人だけ6秒へ変更。実際の収録開始から時間を数える | 長く撮らなくてよい |
| 音のヒント | 画面下に「コツン」「サーッ」「カチカチ」など任意のヒント | 家の中で探したくなる |
| 取り込み | PhotosPickerで選んだ動画を読み込み、最大6秒を選択 | すでにある映像も使える |
| 自動切り出し | 音の立ち上がりを候補にし、無音を短くする。いつでも元に戻せる | 難しい編集が不要 |
| 3アレンジ | 「ぽつぽつ」「ゆらゆら」「にぎやか」。同じ素材で密度・スウィング・伴奏を変える | 意外な聴こえ方に出会える |
| 素材のまま / 曲 | 同じ3素材の短い比較再生を一操作で切り替える | 何が変わったか分かる |
| もうひとつ | 種を変えて別配置を作る。以前の候補に戻せる | 納得するまで試せる |
| かんたん調整 | 素材ごとの音量、伴奏量、切り出し位置だけを前面に出す | 自分の音を主役にできる |
| 動画3レイアウト | 3段、順番に大きく、フォトダンプ。どれも同じ曲を使う | 投稿の雰囲気を選べる |
| 字幕 | 物の名前と短い一言。編集・非表示可。自動文字起こしは必須にしない | 自分の言葉で残せる |
| 自動下書き | 素材確定と編集確定時に保存。異常終了しても復元 | 作ったものを失いにくい |
| 再利用 | 素材を複数の作品から参照。複製して使える | 自分の音の収集が楽しくなる |
| 共有ファイル | 選んだ音付きクリップと編集情報をまとめ、別端末で再編集 | 友だちが参加できる |
| 内蔵お題 | 「朝の3音」「台所だけ」など、達成義務のないカード | 次に撮るきっかけ |

「もうひとつ」は録音をやり直さない。元の候補を履歴から戻せる。
音名は手入力または候補から選択。物体認識を必須要件にしない。

## 6. アートディレクション

### 共通

- 参考は既存の「14-open-lid-mobile-ui.png」。完成素材ではなく方向性の資料。
- 画面は普通の長方形。セーフエリア、Dynamic Island、ホームインジケータを避ける。
- 動画の占有率を高く保つ。飾りが動画より目立つ場合は飾りを小さくする。
- 実物のモチーフは上端・下端の形と手触りに使う。操作を別のゲームへ変えない。
- システムフォントを基本に、短い字幕のみラフな手書き風を選べる。
- 主操作は柔らかな紫、録画は珊瑚色。文字は十分な明暗差を確保する。
- 通常タップ領域は最低44ptを基準とする。模様の形とヒット領域を混同しない。
- 道具の外観は部品化して差し替え可能にする。画面ロジックへ埋め込まない。

### 撮影: 蓋が開いたコーヒー

上端に蓋の裏側を少し見せ、下端にカップの飲み口と上部を置く。
左右にカップの側面は描かない。映像は左右端まで使う。
蓋と飲み口の合計高さは標準文字サイズで有効画面の約25%以内を目標にする。
小型端末や大きな文字では立体部分を薄くし、ボタンを優先する。

撮影を開いたときに蓋が少し持ち上がって所定位置へ収まる。
毎回長いオープニングを見せない。カメラの準備は同時に進める。
録画中は蓋・カップを動かさず、映像と録画時間に集中させる。

### つくる: クリップボード

上部に小さな金属クリップ。3素材のカードは素直な縦並び。
新しい素材が一覧の空いている位置へ着地する。装飾は固定、カードが主役。
長押し並べ替えは指に追随。VoiceOverからも上下移動できる。
カードのドラッグだけに依存せず、メニューで順序を変更できる。

### 音づくり・完成: 小さなテレビ

上端と下端だけに控えめな樹脂の質感。映像の周りに太いテレビ枠を作らない。
再生中の素材には細い縁と短い字幕反応を付ける。全画面フラッシュは使わない。
保存・共有は見慣れたアイコンと日本語を残す。装飾のダイヤルに置き換えない。

### その他の画面

「作品」は静かな動画棚、「音の引き出し」は名前どおりの収納感を少し使う。
画面ごとに別の道具を使っても、文字・余白・主操作の色・戻る位置は統一する。
装飾量を「標準 / 控えめ」で選べる。控えめでも主要機能は変わらない。

## 7. 触って気持ちよくする設計

中心の動き: **生活の断片が集まり、同じ拍を持つひとつの動画へまとまる。**
因果: 撮る → 素材カードが増える → 音の役割がそろう → 曲になる → 共有できる。

| 場面 | 反応と目標時間 | 触覚・音 | 割り込みとアクセシビリティ |
| --- | --- | --- | --- |
| ボタンに触れる | touch-downから次の描画で縮み始める。目安0.97倍 | 決定時に軽い触覚、必要な場所のみ | 指を外へ逃がすとキャンセル |
| 撮影を開く | 蓋を180〜260ms程度で位置へ。カメラ準備と並行 | 装飾音は鳴らさない | 途中で閉じられる。Reduce Motionは静止 |
| 録画開始 | 押下反応は即時。準備完了・実データ受信で録画リング開始 | 録画中は触覚もUI音も止める | 準備中を録画済みに見せない |
| 撮影確定 | サムネイルが一覧へ移り、枠が一度だけ沈む | 保存確定後に一回 | 保存失敗なら着地成功を表示しない |
| 並べ替え | 指と1:1で移動。離した速度を受けて収まる | スロットが確定したときのみ | 再びつかめる。メニューでも操作可 |
| 曲を作る | 素材カードが配置へ収まり、準備後に音が順に加わる | 実際の自分の音が報酬 | 演出待ちを足さない。中止可能 |
| アレンジ切替 | 現在の曲を保ち、新候補の準備後に拍境界で切替 | 曲の断裂を抑える短いクロスフェード | 最新選択を優先。前候補へ戻れる |
| 保存完了 | ボタンが一度沈みチェックに変わる | OS保存成功後に完了触覚 | シェア先への投稿成功とは区別 |
| シート開閉 | 操作元から自然につながる標準シート | 追加音なし | スワイプ・戻る・VoiceOver対応 |

設計値は出発点であり実機で調整する。スプリングは原則オーバーシュートを抑え、
ユーザーが投げた・並べ替えた操作だけ少し弾ませる。ループ装飾や毎拍の振動は使わない。

### 録音を汚さない

録画開始の押下触覚を出す場合は記録開始より前に終える。まず無触覚で実装し、実機比較で採用を決める。
撮影中のカウント音、確認音、背景プレビュー再生、触覚を禁止する。
開始後のマイク入力に意図せずUI音が混ざらないことを実機で確認する。

### 動きの3つの見せ場

1. 空の素材欄に、たった今撮った生活が収まる。
2. 1音 → 2音 → 3音と加わり、曲に変わったことが聴いて分かる。
3. 完成後も同じ動画が再生し続け、保存や共有に移れる。

静止時は動画を邪魔せず、変化は意味のある瞬間に集中させる。
大きな移動・回転はReduce Motionで省略し、選択枠・文言・短い色変化で状態を伝える。

## 8. 音を曲にする仕様

### 初版の方式

決定的なアレンジエンジンを採用する。入力、seed、テンプレート版、解析版、レンダラー版が同じなら、同じ曲になる。
配置ルールとPRNG仕様はDart側に固定し、iOS側は生成済みrecipeを解釈する。
外部生成AIに動画や音を送ることを基本フローに含めない。
素材そのものの特徴を残し、オリジナルの小さな伴奏を加える。伴奏はゼロにもできる。

**録った物が判別できることが合格条件。** 無理なピッチ変更で全部をドラム化しない。

### 処理の流れ

1. 元動画を保持し、音声を解析用PCMへ変換する。
2. RMS、ピーク、短時間の変化量を測定し、無音・クリッピング・立ち上がりを検出する。
3. 「短い打音」「反復音」「持続音」の候補を決める。信頼が低ければユーザーに短いプレビューで選ばせる。
4. 打音は立ち上がりの少し前から切り、持続音は自然な部分を選ぶ。
5. 端のクリックノイズを短いフェードで抑え、穏やかなゲイン補正をする。強いノイズ除去は既定にしない。
6. アレンジテンプレートの役割へ割り当て、全素材を少なくとも一度は分かる形で使う。
7. 元音を中心にミックスし、最大ピークを抑える。比較試聴後に動画タイムラインを作る。

音量が足りない場合は「音が少し遠いかも」と出し、撮り直しとそのまま使うを選べる。
無音・音声トラックなしは使える素材数に数えない。既存素材を失わず取り直せる。
音の分類は意味認識ではなく信号上の役割推定。コップ・水などの名前はユーザーが編集できる。

### 15秒を自然に終える

初版は内部テンポ128 BPM、4拍子、8小節 = 15秒。
48kHz音声では720,000サンプル、30fps映像では450フレーム。
「ゆらゆら」はハーフタイムの打点・スウィングなどでゆっくり聴かせる。
UIではBPMを必須操作として見せず、固定テンポを前提に仕上げる。
将来テンポ変更を入れる場合は、秒数と小節のどちらを優先するかを別仕様にする。

| 時間 | 役割 |
| --- | --- |
| 0〜1.875秒 | 1つ目の元音が分かる |
| 1.875〜3.750秒 | 2つ目が加わる |
| 3.750〜5.625秒 | 3つ目が加わる |
| 5.625〜13.125秒 | 3〜6素材が音楽として重なる |
| 13.125〜15秒 | 余韻を整え、冒頭に戻っても違和感の少ない終わり |

6素材の場合も最初の紹介は主役3つ、残りは中盤に加える。
初版で任意の曲調を無制限生成すると約束せず、制作した3テンプレートの品質を優先する。

### 音質の受け入れ基準

- 元の3つの音を利用者が聴き分けられる。
- クリックノイズ、耳障りな瞬間的音量差、デジタルクリッピングがない。
- 候補を変えても体感音量が大きく飛ばない。
- スピーカー・有線相当・Bluetoothで試聴し、保存動画でも同じ曲が鳴る。
- 30種類以上の日用品素材で確認。似た打音3つ、持続音3つ、録音が小さい組合せも含む。
- ラウドネスの初期目標は概ね-16〜-14 LUFS、true peak -1 dBTP以下。劣化する場合は数値達成より素材の聴きやすさを優先し、実測で調整する。

## 9. 映像と共有したくなる仕掛け

### 音が鳴った理由を見せる

- 音イベントに合わせて該当クリップに細い輪郭や短い字幕反応を出す。
- 元動画内で音が発生した時刻と、曲中で鳴る時刻を対応付ける。
- 動画をただ順番に貼り、関係ない音を上に載せる実装にしない。
- 持続音の素材は静かなループ、短い打音は発音部分からの短い映像を使う。
- 速い反復時は毎打点で大きく切り替えず、映像は小節や拍でまとめて音だけ繰り返す。

### 3つの見せ方

- 3段: 主役3素材を常に見せ、どの音が鳴ったか分かる。最初の既定。
- 順番に大きく: 活躍している素材を大きくし、残りを小さく置く。
- フォトダンプ: 固定の写真風フレームと短い字幕。素朴な日常動画として残せる。

4〜6素材を使う場合は、中盤の小節境界で表示素材を入れ替え、使った全素材が一度は見えるようにする。
各レイアウトはArrangement内の音イベントと同じ素材IDを参照する。

字幕は各動画内の安全領域へ配置し、投稿先のUIに埋もれにくい余白を設ける。
TikTokなどの安全領域は変わり得るため、投稿前の実アプリプレビューで確認できる説明を付ける。
投稿先への直接自動投稿は行わない。共有先をユーザーが選ぶ。

### 共有の設計

- 通常共有: 1080×1920のH.264/AAC MP4。iOS共有シートを開く。
- 写真保存: ユーザーが保存を押したときに追加権限を要求し、成功を確認する。
- 作品名: 短い提案を出すが、手入力・空欄・字幕なしを選べる。
- 小さなアプリ名表記: 既定で付ける提案。無料でも非表示にできる。共有を邪魔する大きな透かしは付けない。
- リミックス: .otogurashiファイルに選択した素材とmanifestを入れる。SNS動画から元素材を自動復元できるとは表示しない。
- 共有シート完了とSNS投稿完了を同一視しない。「共有画面を開いた」「書き出した」を別イベントにする。

## 10. データと保存

### エンティティ

| 型 | 主な情報 |
| --- | --- |
| ClipAsset | ID、相対ファイルパス、長さ、向き、撮影日時、名前、波形、ハッシュ |
| SoundSlice | Clip ID、切り出し始点/長さ、ゲイン、分類候補、元映像の発音位置 |
| Project | ID、タイトル、Clip参照、作成/更新時刻、現在の編集リビジョン |
| Arrangement | Template ID/版、seed、15秒のイベント列、各素材ゲイン、伴奏設定 |
| VideoRecipe | レイアウト、素材ごとのクロップ、字幕、安全領域、映像イベント |
| ExportJob | Project/revision、開始時刻、状態、出力先、一時ファイル、失敗内容 |
| RemixManifest | スキーマ版、選択素材、編集情報、任意作者名、ファイルハッシュ |
| Preferences | 触覚、装飾量、既定画質、字幕、オンボーディング状態 |

原本の動画はApplication Support配下、DBには巨大な映像を入れず相対参照を持たせる。
解析キャッシュ・プレビュー・一時書き出しは再生成可能な領域へ分ける。
DB保存と原本移動は一時状態を経て確定し、途中終了で壊れた参照を残さない。
起動時に未完了ジョブと一時ファイルを照合し、続行または安全なやり直しを提案する。

### 削除

完成作品を削除しても、別の作品で使う素材は消さない。
素材削除前に参照作品を確認し、「作品から外して削除」を明示する。
簡単に取り消せる削除は短いUndoを用意。端末からの最終削除は確認する。
バックアップ対象は原本と編集データ、キャッシュは除外。容量画面で内訳を示す。

### リミックスファイル

manifest + mediaのZIPコンテナを提案。初版上限6素材、展開後合計150MB。
相対パスのみ許可し、../・絶対パス・シンボリックリンク・未知の実行形式を拒否する。
manifest版、長さ、実メディア形式、ハッシュを検証し、展開後も上限を確認する。
取り込みは新規Projectへコピーし、既存作品を上書きしない。
相手へ渡す素材一覧を事前表示。端末位置情報は共有用ファイルに引き継がない。
未知の新しいスキーマ版なら、壊して読み込まず更新が必要な旨を示す。

## 11. 技術構成と責務

### 比較

| 方針 | 長所 | 今回の判断 |
| --- | --- | --- |
| SwiftUI + Apple標準メディアAPI | 音声・映像・触覚・OS連携を直接扱える | 当初案。将来UIを転用しやすくするため、画面全体のSwiftUI実装は採用しない |
| Flutter/Dart + 必要なiOSネイティブ処理 | 画面・編集ロジックを再利用でき、媒体処理はOSに適した実装を使える | 現在の設計方針。開発・動作検証はiOSに絞る |
| サーバーで曲と動画を生成 | 重い処理を端末外へ出せる | 通信・費用・待ち時間が初回体験に乗るため将来評価 |

### 共通化の範囲と初版の境界

Flutter/Dart側に画面、道具モチーフ、アニメーション、編集状態、曲の配置ルール、字幕・エフェクトの設定、保存データの定義を置く。
カメラ、音声解析・レンダリング、動画合成、写真保存、共有、触覚等はサービスの境界で分け、初版ではiOSで必要な実装だけを完成させる。
既存プラグインで満たせる処理は利用し、精密な同期や媒体処理で不足するところのみSwift等で補う。
OS間の呼び出しには指示・設定・ファイル参照を渡す。録画中の全映像フレームや音声バッファをDartとの間で往復させる設計にはしない。

Android用の媒体処理、権限・端末差対応、ビルド設定、実機テストは将来の移植作業として残る。
Android対応済み・ビルドするだけで完成・両OSで同じ触覚や音質を保証、といった扱いにはしない。
初版にAndroid専用画面・CIジョブ・ダミー実装・ストア設定を作らない。将来のためだけの複雑な共通媒体エンジンも作らない。
プラグイン選定時はAndroid実装の有無も参考にするが、初版のiOSでの品質を優先する。

### モジュール

- App: 起動、ナビゲーション、依存の組み立て。
- Features: Capture / Create / Arrange / Library / Share / Settings。Flutterの画面と状態を持つ。
- Domain: DartのProject、Clip、Arrangement、編集コマンド。FlutterのWidget・AVFoundationに依存しない。
- MediaServices: 撮影・解析・音声出力・動画出力の共通の呼び出し口。実装はiOSから用意する。
- iOS Capture: AVCaptureSessionまたはカメラプラグインのiOS実装。録画、入力状態、向き、割り込み。
- iOS Audio: 音声解析、切り出し、ミックス書き出し。テンプレート配置ルールはDomain側。
- iOS Video: 共通recipeからの映像構成、字幕、書き出し、プレビュー。
- Storage: 共通データスキーマ、DB、原本、キャッシュ、移行、共有ファイル。OSのファイル保存先はアダプターから取得する。
- DesignSystem: Flutterの色、文字、ボタン、道具モチーフ、動き。触覚はサービス越しに要求する。

外部依存は必要性を確認してから導入し、初版の音声処理はApple標準APIを第一選択にする。
永続化はSQLite等の移植可能な方式を選定し、SwiftDataを共有データモデルの前提にしない。

### 設計上の契約

CaptureServiceは録画状態と保存済みClipを返す。UIにAVCaptureSessionの所有を持たせない。
ArrangementEngineはClip解析とTemplate/seedを入力に、決定的なArrangementを返す。
AudioRendererはArrangementから正確に15秒の音を作る。
VideoRendererは同じArrangementの時刻を使い、映像と音を合成する。
ProjectStoreは編集リビジョンを保存し、画面遷移とは独立して動作する。
ExportCoordinatorは同時書き出しを1件に制限し、中止・再試行・完了を管理する。

### 音・映像の同期

時刻の唯一の基準はArrangementの時間軸。
UIタイマーやアニメーション終了を音の発音基準にしない。
共通recipeは整数サンプル位置や有理数の時間で保持し、Apple固有のCMTimeを保存形式に含めない。
音は48kHzのサンプル位置、映像はiOS側でCMTimeと30fpsのフレーム位置へ変換する。
丸めは各イベントの絶対時刻から計算し、前イベントへの加算によるドリフトを避ける。
128 BPMでは1拍が30fpsの整数フレームにならないため、音声時刻を正として最も近い映像フレームへ丸める。同点は後のフレームへ寄せる。
内部PCMの720,000サンプルとAACの復号サンプル数は同一視しない。MP4は表示時間15秒、450映像フレーム、先頭・末尾の余分音と同期を別々に検証する。
プレビューも書き出しも同じrecipeを利用。簡易プレビューのみ別の曲にしない。
初版は低解像度の完成動画を先に作りAVPlayerで再生、1080p書き出しを確定操作後に行う方式を基準とする。
解析・曲生成だけを先に終えた段階では、完成動画として偽の成功表示を出さない。

### 採用候補技術・API

共通部分はFlutter/Dart。UI部品・編集状態・データモデルとiOS媒体処理を分離する。
iOS部分の候補はAVFoundation、AVFAudio/AVAudioEngine、Accelerate、Core Image、PhotosUI、UIActivityViewController、UniformTypeIdentifiers。
OS機能はプラグインまたは型を定義したplatform channel越しに利用する。追加する依存と版は実装計画で固定する。
Core Hapticsは複雑な触覚が本当に必要な場合のみ。最初は標準feedback APIで足りる範囲にする。
映像合成はAVVideoComposition / AVVideoCompositingを候補とし、プロファイル後に必要な処理だけMetalへ下げる。
Flutter・Dart・Xcode・Swift・SDKの具体版はGitHub Actions環境を選んだ時点で固定し、実行ログへ記録する。

## 12. 状態遷移と失敗からの回復

### 撮影

idle → requestingPermission → preparing → ready → recording → finalizing → review
権限拒否: ライブラリ取り込みとサンプル体験を残す。必要なら設定への導線を出す。
電話割り込み: recordingからinterruptedへ。十分な有効データがあれば確認へ、なければ再撮影へ。
画面離脱: 保存完了を待つ必要がある場合もUIを固めず、現在の状態を説明する。
録画の最大時間は実データのタイムスタンプで決定する。

### 生成

idle → analyzing → arranging → renderingPreview → ready
cancelled / failedから下書きへ戻れる。進行表示は実処理段階から更新する。
新しいアレンジを要求したら古い非表示ジョブを取り消す。編集中のProject revisionが変わったら古い結果を採用しない。
裏で処理が終わっても、別作品へ移ったユーザーを強制的に戻さない。

### 書き出し

queued → renderingAudio → renderingVideo → validating → readyToShare
映像と音の長さ、トラック、読み出し可能性を確認してから成功にする。
Photosへの保存は別の状態で管理。ファイル作成成功と写真保存成功を分ける。
バックグラウンド実行はOSに保証されない。中断したら前景復帰後に再試行できる状態を保存する。

### 重要な異常系

| 状況 | 振る舞い |
| --- | --- |
| 音のない動画 | その素材を使えない理由と差し替え導線 |
| ファイルがiCloudから未取得 | 取り込み中表示、キャンセル可 |
| ストレージ不足 | 必要容量の目安とキャッシュ整理。原本を勝手に消さない |
| Bluetooth切断 | 再生停止。勝手にスピーカーへ大音量出力しない |
| 音声入力ルート変更 | 録画を止めて入力を再設定。途中のフォーマット変更を混ぜない |
| アプリ終了 | 確定済み素材と下書きを復元 |
| 共有キャンセル | 作品は残る。共有成功扱いにしない |
| 同じボタン連打 | ジョブIDで重複を抑える。視覚反応は残す |
| 低電力・発熱 | プレビュー品質を下げる提案、出力品質は勝手に変更しない |

## 13. プライバシー・権利・利用しやすさ

- カメラ・マイク権限は初回撮影時に理由を添えて要求する。
- 写真は選択式読み込み、保存は必要な追加権限だけを要求する。
- 動画・音声を分析サーバーへ自動送信しない。録画場所の位置権限も不要。
- 伴奏と内蔵サンプルは自作または利用権が確認できる素材に限定し、出所を記録する。
- 共有前のプレビューで、映り込みや会話を確認できる。外部への自動投稿はしない。
- VoiceOverで各素材の名前・長さ・選択状態が読める。
- 大きい文字では装飾を縮小し、操作をスクロール領域へ逃がす。
- 音を聴けない状況でも、録音の有無・生成完了・エラーが視覚で分かる。
- 触覚オフ、Reduce Motion、Increase Contrastに対応する。

これは公開SNSではないため、初版で公開投稿の監視機構を持ち込まない。
将来公開フィードを追加する場合は、通報・ブロック・削除とApp Review要件を含めて別設計する。

## 15. GitHub Actions → TestFlight

ユーザーの既存の配布方法に合わせる。開発先はユーザー指定のyurashu2-droid/OtoGrashi。Flutterアプリはこの独立したリポジトリで管理し、そのiOSターゲットをビルドする。
新しいGitHubリポジトリ名・Bundle ID・Team IDは勝手に作らず、接続時に既存設定を確認する。

### CIの役割

1. 通常の変更: Dart/Flutterの静的解析・単体/Widgetテストを行い、macOS runnerでiOSビルドとSimulator統合テストを行う。
2. 内部配布: 指定したコミットをarchive/exportし、署名後にTestFlightへアップロード。
3. Apple側の処理完了とテスターへの配布可能状態は、アップロード成功とは分けて確認。
4. 実機で収録品質・音の同期・触覚・メモリ・発熱を確認し、その結果を次の変更へ戻す。

初版のCIにAndroidビルド・エミュレータテスト・配布は含めない。共通ロジックのテストは行うが、Androidでの動作確認の代わりにはしない。

最初はworkflow_dispatchで配布を明示的に起動する構成を提案する。
PRチェックでは署名用の秘密情報を使わない。配布ジョブのみGitHub Environmentから取り出す。
macOS runnerラベルとXcode選択は固定し、存在する実環境を確認して導入する。
「latest」の暗黙更新だけに依存しない。依存解決結果・Xcode版・commit SHAを成果物に記録する。

### 接続時に必要な設定名

- Bundle ID、Team ID、App Store Connectのアプリ識別情報
- 既存配布方式に合わせた署名証明書・Provisioning Profile
- App Store Connect API key ID / issuer ID / private key
- 配布先TestFlightグループ、既存ワークフローの有無

秘密値をチャットへ貼る必要はない。GitHub Secrets/Environment経由で設定する。
既存の署名方式がある場合は、その方式に合わせて重複を作らない。
証明書を一時Keychainへ読み込み、ジョブ終了時に片付ける。
この設計時点ではリポジトリ作成・秘密情報登録・配布は行っていない。

### 成果物

.ipa、.dSYM、.xcresult、テスト結果、使用環境、変更説明、実機チェック表。
TestFlightのWhat to Testには、そのビルドで確認したい操作を短く書く。

## 16. 品質とリリース判定

以下の数値は未計測の受け入れ目標。対応する実機のうち性能が低い機種で測り、必要なら仕様を調整する。

| 項目 | 初期目標 |
| --- | --- |
| 押下の視覚反応 | 次の描画フレームから開始 |
| 初回体験 | 内蔵例から60秒以内に意味が分かる |
| 初回制作 | 撮る対象を選ぶ時間を除き、3素材から完成まで迷わず進める |
| プレビュー準備 | 3素材・標準設定で10秒以内を目標。超える場合も取消可能 |
| 1080p書き出し | 標準15秒で30秒以内を目標 |
| 音・映像同期 | 書き出し内の基準イベント差が1フレーム以内を目標 |
| 動画長 | 450フレーム、音声720,000サンプルを基準に確認 |
| 中断復元 | 確定済み素材を失わず下書きへ戻れる |
| UI | 主要操作44pt以上、標準とアクセシビリティ文字サイズで確認 |
| 体験評価 | 初見5人で、元音の判別・撮り直し・共有までを観察する |

### 意味のある自動検証

- Arrangementが同じ入力・seedで再現し、イベントが15秒を超えない。
- 全素材が割り当てられ、無音入力・短い素材・持続音だけでも破綻しない。
- PCM長と映像フレーム、音と動画の対応するイベント時刻を検証する。
- 正規化・端フェード・リミットでNaN、無限大、クリッピングを生まない。
- 保存途中の終了、古いリビジョンの生成結果、素材参照削除の整合性を検証する。
- 共有ファイルの不正パス、巨大展開、欠損メディア、未知版を拒否する。
- Simulatorでサンプル作品からプレビュー・書き出し・再編集の導線を確認する。

### iPhoneでしか合否を決めない項目

- 実録画の音量・ノイズ・端末振動混入・映像との同期。
- Bluetooth、電話、バックグラウンド移動、入力ルート変更。
- 片手での押しやすさ、連打、途中で戻る、ジェスチャー中の方向反転。
- 保存動画を写真アプリと共有先で再生したときの音・文字・クロップ。
- 発熱とメモリ、連続で10作品作ったときの劣化。
- Reduce Motion・大きい文字・VoiceOver。

Simulatorの成功だけで「録音品質確認済み」「触って気持ちよい」とは扱わない。
現時点では設計レビューのみで、これらのテストはまだ実施していない。

## 17. 作る順番の考え方

製品全体の設計を固定したうえで、最初に不確実な「3音が気持ちよく曲になる」部分を通す。
次にその時間軸から動画を作り、撮影・保存・共有を接続する。
装飾と動きは後付けにせず、各画面が動いた段階で同時に仕上げる。
最後に権限・中断・データ復元・アクセシビリティを検証して初版を完成させる。
これは実装の詳細作業計画ではない。設計確認後、ファイルと検証手順に落とした計画を作成する。

設計段階で残る外部設定はGitHubの対象リポジトリ、署名先アプリ、配布グループ、実機の機種/OS。
具体的な値が未確認でも、ローカル処理の設計はこのまま進められる。

### 初版後の追加機能: 音・映像連動エフェクト

ユーザー指定の将来機能。**サウンドエフェクトとビデオエフェクトを、同じ世界観のセットとして適用できる。**
初版の完成条件・初回TestFlightの実装範囲には含めない。初版の3アレンジや3動画レイアウトとは別の拡張として扱う。

代表例は「16bitゲーム風」。録った生活音をレトロゲーム調に加工し、同時に映像を紫系の限られた色数とドット絵の見た目へ変える。
ここでの16bitは表現テーマの呼び名。保存音声を16bitに変換するだけでこの効果になる、という仕様にはしない。
音の加工方法は追加機能の実装時に聴き比べて選び、元の道具の音が分かる範囲を残す。

| セット | サウンド側 | ビデオ側 | 位置付け |
| --- | --- | --- | --- |
| 16bitゲーム風 | レトロゲーム調の音色・粒立ち、短い電子的な余韻 | ドット絵化、紫系パレット、発音に合わせた小さなピクセルの反応 | ユーザー指定の代表例 |
| カセット日記 | 穏やかな揺らぎとテープ風の質感 | 退色した色、控えめな粒子と映像の揺れ | 将来の候補 |
| 水の中 | 柔らかくこもる音と水中を思わせる余韻 | 青緑系の色、水面のような緩いゆがみ | 将来の候補 |

#### 操作の案

- 音づくり・完成画面から「音と映像のエフェクト」を開き、セットを選ぶ。
- 一つの選択で音と映像の両方が変わる。まず共通の「強さ」だけで調整できるようにする。
- 「元と比べる」で同じ再生位置の加工前後を比較する。「なし」で元に戻せる。
- 詳細調整では音と映像それぞれの強さを変えられる案とし、最初の画面では複雑にしない。
- 加工は非破壊。元動画・元音・編曲を保持し、プレビューと書き出しに同じ設定を適用する。
- 字幕、保存・共有ボタンなどの操作UIはドット絵化の対象にせず、読める状態を保つ。

#### 初版の設計で備えておく境界

音声レンダリングと映像レンダリングの間で共通のEffectRecipeを参照できる構造を想定する。
追加時の情報はpreset ID、preset version、共通の強さ、個別強さ、seed、処理順序。
初版ではエフェクト処理や未完成メニューを実装せず、「指定なし」を通常の描画・音声出力として扱えるようにしておく。
効果を追加した後は、保存作品とリミックス用manifestにも設定と版を持たせる。
未対応の効果を含むファイルは黙って別の見た目にせず、更新案内またはユーザーが選ぶ効果なしの読み込みにする。

音に合わせた映像反応は既存のArrangement時間軸を使う。効果による音声遅延も補正し、書き出しの同期を維持する。
加工後の音量差・クリッピング、映像のちらつき、文字の可読性、実機での処理負荷を追加時に検証する。
Reduce Motionではドット絵・配色など静的な特徴を残し、揺れや点滅を抑える。

## 19. 設計セルフレビュー

- 元のコンセプトを維持: 音付き生活動画から曲と動画を作る。物体演奏アプリへ広げていない。
- ユーザーのUI修正を反映: 長方形内、撮影画面のみ蓋/飲み口、左右枠なし、他画面は別モチーフ。
- 15秒と小節数の関係を定義: 128 BPM、8小節。
- 成功表示を実処理完了に結び付けた。アニメーションの時間切れを成功扱いにしない。
- 元動画・音・映像イベントを共通時間軸で扱い、プレビューと書き出しの食い違いを防ぐ。
- 本体の状態・媒体処理・装飾を分離し、後から見た目を変えやすい。
- クラウド必須・公開SNS必須・Mac所有必須という前提を置いていない。
- 性能目標と実測、設計と実装を区別した。
- 配布可能になるまでの署名・ビルド・Apple側処理・実機確認を区別した。
- iOSのみ検証する今回の範囲と、Flutterによって将来再利用できる範囲を区別した。Androidの完成・動作保証は初版に含めない。
